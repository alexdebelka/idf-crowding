# PWA: offline shell and opened stations, caching headers, a CSP for the site's own origin

The app is installable (web manifest, icons) and works offline for what the visitor has already used: the home, the method page, and every station they opened recently, with its date forecasts. Everything is served from the site's own origin (promise "Gratuit, sans compte, sans traceur": no analytics, no third-party request of any kind). The service worker is plain JavaScript (`app/public/sw.js`), registered in production only (`RegisterSW`), scope `/`, with no library.

## Service worker

Caches (all names carry a `VERSION` constant):

| Cache | Content | Bound |
|---|---|---|
| `apoint-shell-<v>` | `/`, `/a-propos/`, fonts, `/brand/*`, `/icons/*`, files under `/_next/static/` | the newest 150 files under `/_next/static/` (oldest dropped) |
| `apoint-stations-<v>` | per station: `/p/<id>/`, its Next.js payload files (`index.txt` and the segment files), `/data/places/<id>.json`, plus one small list of the most recent ids | 8 stations (the home shows 4), least recently opened dropped first |
| `apoint-data-<v>` | other files under `/data/` (the index) | a few files |

Strategies (the decisions are pure functions at the top of `sw.js`, tested in `app/test/pwa-sw.test.ts`):

- **Navigations** (`/`, `/a-propos/`, `/p/<id>/`, any other page): network first, a cached copy after 4 s or when offline. A page that was never cached while offline: a redirect to the cached home. A 5xx response is replaced by the cached copy; a 404 is shown as is.
- **Next.js payload files** (`__next*.txt`, `index.txt`, read by client-side navigation): network first, same fallback. If one is missing offline, Next.js falls back to a normal navigation, which the rule above answers.
- **`/_next/static/*`, `/fonts/*`**: cache first (the names are hashed, or the font is versioned by its file name).
- **`/brand/*`, `/icons/*`**: stale-while-revalidate.
- **`/data/*`**: stale-while-revalidate, with a conditional request (`cache: no-cache`) on every use: a new data release replaces the cached copy at the next use (the first view after a release can still show the previous copy).
- Not touched: other origins, anything but GET, range requests, `/sw.js`, the manifest, `/cdn-cgi/*`.
- Only complete same-origin 200 responses are stored (never opaque, redirected, partial, failed or `no-store`).

A station counts as opened when its page is navigated to, or when the page tells the worker (`RegisterSW` posts `{ type: "station-opened", id }` for every `/p/<id>/` path, which covers client-side links: those never load the page's HTML, so the worker cannot see them). The Place file that the home fetches for its tiles, and payloads prefetched for visible links, do not count. Opening moves the station to the front of the recent list; stations beyond 8 and stations that were only prefetched are purged; and whatever is missing among its page (with the files it names), its full payload and its Place file (the home reads it for the tile) is fetched once, so that a reload offline works and its tile shows its state. A station page embeds its own data (the date forecasts are in the page), so an opened station needs nothing else offline.

**Update behaviour.** `sw.js` is served with `max-age=0, must-revalidate` and registered with `updateViaCache: "none"`, so the browser compares it with the network on navigations. A new worker installs (it re-fetches the home, the method page, the fonts and the files they name), takes over at once (`skipWaiting`, `clients.claim`) and deletes every `apoint-*` cache whose name is not the current one. A deploy of the site needs no change in `sw.js`: pages are network first, hashed files never change under one name, data is revalidated. Bump `VERSION` only when the worker's own logic or cache layout changes; this also empties the stations cache (a visitor re-opens the stations they need). Nothing can be stale forever: the worker file is never cached for long, pages and payloads try the network first, data is revalidated on every use, and every cache is bounded or versioned.

## Cloudflare Workers static assets

`app/wrangler.jsonc` serves `./out` with `html_handling: "auto-trailing-slash"` (the default; with `trailingSlash: true` a page is `dir/index.html` served at `/dir/`, and the other form gets a 307) and `not_found_handling: "404-page"` (the nearest `404.html`, status 404). No Worker script, no `run_worker_first`: every request is a static asset request, which is free and unlimited, and `_headers` applies (it does not apply to responses generated by a Worker).

`app/public/_headers` is copied to `out/_headers` by the build; it is read by Workers and not served as an asset. Verified against the documentation (see References): one block per URL pattern with indented `name: value` lines, `*` splat (one per URL), at most 100 rules and 2,000 characters per line, every matching block applies in file order, and a header set by several blocks is joined with a comma. That last rule breaks `Cache-Control` (conflicting directives), so the Cache-Control blocks never overlap (checked in `pwa-config.test.ts`). Defaults when nothing is set: `Cache-Control: public, max-age=0, must-revalidate` with an `ETag`; HTML and payload files keep it.

| Pattern | Cache-Control |
|---|---|
| `/_next/static/*` | `public, max-age=31536000, immutable` |
| `/fonts/*` | `public, max-age=31536000, immutable` |
| `/brand/*`, `/icons/*` | `public, max-age=2592000` |
| `/data/*` | `public, max-age=300, must-revalidate` (monthly release visible within minutes; 304 when unchanged) |
| `/sw.js`, `/manifest.webmanifest` | `public, max-age=0, must-revalidate` |

Security headers on `/*`: `Content-Security-Policy`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Permissions-Policy` (camera, microphone, geolocation, payment, usb, sensors, topics all off).

**CSP trade-off.** `default-src 'self'` with `connect-src`, `font-src`, `manifest-src`, `worker-src`, `media-src` on `'self'`, `img-src 'self' data:`, `object-src 'none'`, `base-uri`, `form-action` on `'self'`, `frame-ancestors 'none'`: no other origin can be named, which enforces the promise in the browser, in addition to `scripts/check-export.mjs` in CI. `script-src` keeps `'unsafe-inline'`: the Next.js static export writes its bootstrap and its payload as inline scripts in every page, and a nonce is impossible without a server. A hash list would have to change with every page (538 station pages) and every build, and `_headers` is limited to 100 rules and 2,000 characters per line. Consequence: the CSP does not stop an injected inline script; it still stops loading code from, or sending data to, any other origin. The site has no user input stored or rendered as HTML, no cookies and no account, which keeps the exposure small. `style-src` keeps `'unsafe-inline'` for the same reason (style attributes). No `'unsafe-eval'`. Revisit if Next.js offers hash-based CSP for static exports.

## Guard: no other origin

`app/scripts/check-export.mjs out` runs in CI after `next build`. It fails when a file of the export references another origin in a way a browser would request (script, link, img, srcset, iframe, form action, CSS `url()` / `@import`, `fetch`-like calls with a literal URL, absolute URLs in code, manifest values), when a font, analytics or tracking host is named anywhere (including the data files), when `manifest.webmanifest`, `sw.js`, the icons (declared sizes checked), `_headers` (CSP names `'self'` only) or the fonts are missing. Plain `<a href>` links are allowed to the source and licence pages only (`data.iledefrance-mobilites.fr`, `opendatacommons.org`) and are listed in the output. Framework strings that look like URLs but are never requested (React error links, XML namespaces, a core-js test string) are on a short allow list in the script. It cannot see what Cloudflare itself injects at the edge: see the next section.

## What the Cloudflare dashboard shows (for traffic)

Documented: Workers metrics (dashboard, Workers & Pages, the Worker) show request counts (total, success, errors), subrequests, invocation statuses and CPU time per Worker, kept 3 months; zone analytics (a domain on Cloudflare) count requests served to visitors, bandwidth, status codes. Requests to static assets are free and unlimited; the 100,000 requests per day of the free plan concerns Worker invocations. Not documented in the pages read: whether a site made only of static assets (no Worker invocation) fills the Workers request graph, any per-path count, any count of visits or unique visitors. Cloudflare Web Analytics gives pages and visitors but needs a JavaScript beacon (automatic injection is on by default for a proxied hostname once added): it is not "sans traceur" and it would be blocked by the CSP. **To confirm at deploy:** which graphs fill on a `workers.dev` URL and on a custom domain, on the owner's plan; and that no Web Analytics beacon is injected (`curl` the home and search for `cloudflareinsights`; keep Web Analytics disabled for the hostname, or use the "Disable Real User Monitoring" configuration rule).

## Considered options

- **A caching library (Workbox):** a runtime dependency (not allowed without asking) for about 300 lines of logic that must be understood and tested anyway.
- **Precaching every station:** 538 pages and payloads, about 30 MB for something most visitors never open.
- **Cache first for pages:** a deploy would not reach returning visitors until the next worker update.
- **Hash-based CSP:** see the trade-off above.
- **Showing an "update available" prompt:** no design for it; the worker takes over at once and pages are network first, so none is needed.

## Consequences

- Offline works for the home, the method page and the last 8 opened stations; search needs the index baked in the home page (it is, today) and unopened stations need the network (the visitor lands on the home).
- The recent list of the worker is independent of the 4 stations shown by the home (`lib/saved.ts`): opening a station moves it first in both; the worker keeps 4 more.
- Disk use per visitor: about 1 MB of shell and about 100 KB per opened station.
- The recent list moves only on a page open (navigation or the `station-opened` message), so a route that merely fetches Place files for other stations does not disturb it; the files of stations that are not in the list are purged at the next open.
